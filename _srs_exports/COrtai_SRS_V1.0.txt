1 Introduction
1.1 Purpose
This document defines the complete set of business and engineering requirements that COrtai V1.0 must satisfy before going live with the TownePlace Suites Marriott Vaughan (TPSV) pilot. It serves as the shared reference between the engineering team, the pilot operator and external reviewers (security, privacy, brand).
1.2 Scope
V1.0 covers all eleven product surfaces required to operate a single Marriott TPSV-class property: hotel operations dashboard, physical security and hotel vision, housekeeping mobile app, staff input forms, AI intelligence, unified guest messaging, sales pipeline, staff management, revenue, administration, and security & network. It additionally specifies the ingestion path from distributed edge devices (MQTT JSON), the multi-tenant data model, the deployment architecture (AWS ca-central-1 with VPN-only access) and the acceptance criteria.

2 Overall Description
2.1 Product perspective
COrtai is a vertical hotel operations platform combining edge computer vision, IoT sensing, network security and an AI assistant into a single multi-tenant SaaS, with Marriott TownePlace Suites Vaughan as the first pilot property.
2.2 Product functions (high level)
• Real-time monitoring of cameras and IoT sensors with AI-powered analytics.
• Centralised dashboard for hotel managers and front desk staff.
• Mobile application for housekeeping, maintenance and security staff.
• AI assistant (RAG over the hotel's own data) for natural-language operational questions.
• Unified guest messaging across SMS, WhatsApp, Email and Web Chat.
• Sales pipeline with SLA-tracked inquiry handling.
• Staff management with scheduling and certifications.
• Revenue dashboards and night audit.
• Multi-tenant administration for the service provider.
• Direct ingestion from distributed edge devices via MQTT JSON, with end-to-end persistence and real-time display in the operator UI.
2.3 Operating environment
• Cloud: AWS ca-central-1 (data residency Canada).
• Edge: an edge device per camera cluster and/or distributed edge devices co-located with cameras, plus an optional aggregator per hotel.
• Network: site-to-site VPN between each hotel and the AWS VPC.
• Browsers: Chromium 118+, Firefox 120+, Safari 17+ (latest two majors).
• Mobile: Android 10+ (API 29), iOS 16+.
• OS server: Ubuntu 22.04 LTS.
2.4 Design and implementation constraints
• Single EC2 t3.medium for V1.0 — services must collectively fit in 4 GB RAM with 1.5 GB headroom.
• RDS PostgreSQL 17.6 db.t3.small — schema must remain compatible with TimescaleDB extension availability.
• VPN-only access — no public-internet endpoints.
• Port 80 closed at security-group level — TLS via DNS-01 only.
• Canonical Postgres schema (18 SQL files) is the source of truth; new tables go through migration review.
• Bedrock Claude (claude-sonnet-4-20250514) is the pinned LLM — no model swap without explicit deployment ticket.
• voyage-3 embeddings are pinned; the vector(1536) column type forbids dimension changes.
• All UI strings must support EN + FR (Canadian audience).
• All guest-facing communication must comply with PHIPA / PIPEDA.
2.5 Assumptions and dependencies
• Network Engineering provides timely TLS certificates, DNS records, VPN provisioning and RDS parameter-group changes.
• The edge-device vendor provides firmware updates and SDK support for the duration of the pilot.
• Marriott provides read access to MGS API and Bonvoy GSS for the pilot property.
• Twilio account, WhatsApp Cloud API account, and AWS Bedrock model access are funded by the service provider.
• TPSV property management staff are available for UAT during sprint demos.

5.2 Physical Security & Hotel Vision
Hotel Vision turns each edge device into a real-time analytics engine. It must handle the 28 algorithms in the platform's algorithm library (corridor loitering, tailgating, PPE, fall, smoke, pool capacity, unattended luggage, etc.) and surface them to the operator with the right zone, time-of-day rules and escalation.
▶ NEW: All Hotel-Vision analytics are computed on the edge device; only the JSON detection stream (id, bbox, class, confidence, track id) leaves the edge — never raw video. Live WebRTC playback is direct browser-to-camera inside the property VPN.

5.12 Distributed Edge Ingestion (MQTT JSON)
Beyond the central edge device per camera cluster, the platform must ingest data from a fleet of distributed edge devices co-located with individual cameras and IoT sensors. These distributed nodes publish their detection results, telemetry and health directly via MQTT JSON. Both the backend and the operator UI must be able to retrieve those payloads, persist them in the database, and surface them in real time, without exposing the underlying hardware model name to operators or end-users.
▶ NEW: Single ingestion contract across all edge classes. Both the main edge device and the distributed edge devices publish to the same MQTT broker, with the same JSON schema (envelope: device_id, ts, type, payload). The backend treats every edge node as a peer; the UI shows logical camera / zone bindings only — never the hardware model. This keeps the platform vendor-agnostic and lets the fleet be re-hardware-d without code change.

11 Acceptance Criteria & V1.0 Definition of Done
V1.0 is considered done when every P0 BR and every P0 FR is verified, plus the following platform-wide acceptance items:
• All 9 services running on the EC2 with systemd; survive a reboot without manual intervention.
• End-to-end demo: manager logs in, navigates to Command Center, asks Cortai Intel a question with cited answer, opens Live Camera Grid, an attendant updates a room status from the mobile app.
• Distributed-edge demo: a freshly enrolled distributed edge device begins publishing detections that surface in the operator UI within 5 min of enrolment.
• Pilot UAT: TPSV General Manager and 2 staff members exercise the platform for 5 working days; ≥90 % of P0 user journeys pass.
• Compliance memo signed by counsel covering PHIPA / PIPEDA.
• Pen-test report: no high-severity findings open.
• Backup-and-restore drill executed with all data recovered.
• Documentation: runbook, on-call playbook, API docs, user manual (EN + FR) committed to repo.
• Pricing plan and contract templates ready for the Marriott pitch.
• Trust artifacts: SBOM signed, Trivy scan clean, code-review log archived.
• Cost dashboard: monthly cost on track within 110 % of forecast.
